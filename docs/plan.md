# 小說產生器（Novel Generator）規劃文檔

## 一、專案概述

一款能夠自動生成高品質中文小說的本機 Web 應用程式，在本機瀏覽器中運行，提供從大綱到正文的完整生成流程，並透過 **LLM Wiki + Vector RAG 混合記憶** 確保內容一致性。Multi-Agent 協作引擎為選配功能，於後期階段導入。

### 目標語言
- 中文小說（優先）

### 輸出格式
使用者可選擇以下格式輸出：
- .txt（純文字）
- .html（可閱讀的網頁）
- .epub（電子書格式，含封面與插圖）

### 使用方式
- 本機瀏覽器直接開啟（`index.html` 或 `npx serve`）
- 圖形介面（Web App）

## 三、功能模組

### 3.1 大綱生成系統

**生成流程：**

```
題材/風格輸入 → 用戶點擊'下一步' 
→ 生成世界觀設定/主線劇情架構 → 用戶編輯世界觀設定/主線劇情架構 → 用戶點擊'下一步' 
→ 生成章節大綱 → 用戶編輯章節大綱
```

**輸入欄位：**

| 欄位 | 說明 |
|------|------|
| 題材 | 玄幻/都市/仙俠/科幻/言情/懸疑/自定義 |
| 風格 | 輕鬆/沉重/黑暗/熱血/幽默/爽文/自定義 |
| 由 AI 自動產生 | checkbox，如果打勾則 AI 生成以下輸出欄位 |

**輸出可編輯項：**
- 世界觀設定
- 主線劇情架構
- 章節大綱（可新增/刪除/調整順序）

### 3.3 章節管理器

**運作流程：**
```
設定標題/目標字數/故事節拍/章節要點 → 用戶點擊'生成' → AI 生成正文
```

**核心功能：**
- 新增章節
- 刪除章節
- 修改章節

**章節欄位：**

| 欄位 | 說明 |
|------|------|
| 標題 | 章節標題 |
| 目標字數 | 預設空白。可留空讓 AI 自行發揮 |
| 故事節拍 | 引入/衝突/轉折/高潮/結局/自定義 |
| 章節要點 | 給 AI 生成內容用的額外提示詞（可編輯） |
| 正文 | AI 生成的內容（可編輯） |

**`故事節拍`機制：**

| 節拍類型 | 說明 |
|----------|------|
| 引入 (Inciting Incident) | 故事起因，角色面臨轉折點 |
| 衝突升級 (Rising Action) | 矛盾加深，困難加劇 |
| 中點轉折 (Midpoint Twist) | 重大變化，方向逆轉 |
| 高潮 (Climax) | 最高衝突點，決定性時刻 |
| 結局 (Resolution) | 問題解決，塵埃落定 |
| 鋪墊/過渡 | 連接章節的過渡內容 |
| 自定義 | 用戶手動輸入節拍描述 |

**`故事節拍`運作方式：**

1. AI 根據上一章內容，建議下一章的故事節拍
2. 用戶可選擇接受建議、選擇預設類型、或手動輸入自定義節拍
3. 生成內容時，故事節拍作為系統提示詞的一環引導 AI

### 3.4 知識管理系統（LLM Wiki + Vector RAG + Graph 關係層）

**核心概念：**
採用混合記憶架構，結合結構化 Wiki、向量檢索與圖關係，確保長篇一致性。

**混合記憶組成：**
- **LLM-Wiki**：高階結構化知識（世界觀、角色、劇情線、年表等）
- **Vector RAG**：原始章節全文細節檢索（對話、細節描述、伏筆）
- **Graph 關係層**：實體關係、因果鏈、時間線與約束推理（Phase 2.5 導入）

**Vector RAG 技術說明：**

嵌入向量由本機 Ollama 產生，完全離線運行，無需雲端 API：

| 項目 | 說明 |
|------|------|
| Embedding 模型 | `nomic-embed-text` 或 `mxbai-embed-large`（Ollama 本機） |
| 向量資料庫 | LanceDB（瀏覽器端） |
| 觸發時機 | 章節「存入 Wiki」時同步生成嵌入並存入 LanceDB |
| 檢索時機 | 生成新章節前，Context Budget Manager 自動檢索相關段落 |

**Graph 關係層技術說明：**

Phase 2.5 導入，採用 JSON 圖結構存於 IndexedDB，完全在瀏覽器端運行，不依賴圖資料庫伺服器：

```json
{
  "entities": {
    "char_001": { "name": "李明", "type": "character" }
  },
  "relations": [
    { "from": "char_001", "to": "char_002", "type": "師徒", "since": "ch3" }
  ],
  "events": [
    { "id": "evt_001", "chapter": 5, "cause": "evt_000", "effect": "evt_002" }
  ]
}
```

核心功能：
- 人物關係網視覺化（D3.js 或 React Flow 渲染）
- 基本多跳查詢（透過 JS 遍歷 JSON 圖）
- 提供 Critic Agent（Phase 4）結構化審核依據

**Wiki 內容結構：**

| 類別 | 內容 |
|------|------|
| 世界觀 | 設定、地域、技術、規則 |
| 角色庫 | 所有角色的詳細資訊 |
| 劇情線 | 主線/支線任務進展 |
| 物品/勢力 | 重要物品、組織、勢力 |
| 年表 | 時間線、重要事件 |

**運作流程：**

```
生成章節 → 用戶點擊"存入 Wiki" → 
AI 提取章節關鍵資訊 → 整理進 Wiki + 生成向量嵌入（Ollama） + 更新 Graph JSON →
進行 Lint，找出矛盾、缺少交叉引用 →
下次生成時 → Context Budget Manager 自動載入相關 Wiki + RAG 檢索結果
```

**UI 設計：**
- 每個章節旁邊有「存入 Wiki」按鈕
- 獨立的 Wiki 面板，可查看/編輯已存儲的知識
- 生成新章節時，自動載入 Wiki 中的相關內容到上下文

**未存入 Wiki 提醒機制：**

系統主動偵測尚未存入 Wiki 的已生成章節，避免因遺忘導致 Wiki 內容落後。

- 章節列表中，未存入的章節顯示橘色警示標記 `⚠️ 未存入 Wiki`
- 頂部通知列在有未存入章節時顯示提示：`您有 N 個章節尚未存入 Wiki，建議存入以確保生成一致性。[前往檢視]`
- 點擊「導出」或「生成新章節」前，若有未存入章節，彈出確認提示
- 存入狀態記錄在 IndexedDB 的章節資料結構中，欄位：`wikiSyncedAt: timestamp | null`

### 3.5 章節版本管理

**核心概念：**

每個章節保留最近 3 個生成版本，支援版本比較與釘選，確保用戶不會因重新生成而遺失好的內容。

**版本結構：**

| 欄位 | 說明 |
|------|------|
| versionId | 版本唯一識別碼 |
| createdAt | 生成時間戳 |
| content | 正文內容 |
| prompt | 生成時使用的提示詞（可供參考） |
| isPinned | 是否釘選（釘選版本不受 3 個上限限制） |
| label | 用戶自訂標籤（可選，如「最終版」） |

**運作規則：**

- 每次重新生成，新版本加入版本列表（最多保留最近 3 個非釘選版本）
- 超過上限時，自動刪除最舊的非釘選版本
- 釘選版本不計入 3 個上限，永久保留直到用戶手動解除釘選或刪除
- 用戶可在版本列表中預覽任意版本，並一鍵切換為當前使用版本

**UI 設計：**

```
[第 N 章] ── 版本歷史 ▼
├── ★ v3（當前）  2026-05-08 14:32  [預覽] [釘選]
├──   v2          2026-05-08 13:10  [預覽] [釘選] [刪除]
└── 📌 v1（釘選） 2026-05-08 11:05  [預覽] [設為當前] [解除釘選]
```

### 3.7 Context Budget Manager（上下文預算管理器）

**核心概念：**

負責智慧分配每次生成呼叫的 token 預算，決定「要餵給 AI 哪些內容、以什麼形式、總量是多少」。

**預算分配策略：**

每次生成前，依以下優先順序分配 token 預算（總上限依所選模型 context window 動態調整）：

| 優先級 | 內容 | 預估比例 |
|--------|------|----------|
| 1（必填） | 世界觀設定 + 故事節拍 + 章節要點 | ~10% |
| 2（必填） | 相關 Wiki 條目（已篩選） | ~25% |
| 3（高優先） | Vector RAG 檢索結果 | ~15% |
| 4（高優先） | 上一章 / 指定參考章節（摘要或全文） | ~20% |
| 5（可選） | 更早期章節的壓縮摘要 | ~15% |
| 6（保留） | 輸出緩衝區 | ~15% |

**摘要壓縮策略：**

- 距離當前章節較遠的章節，自動以 AI 壓縮摘要取代全文（摘要長度約為原文 10-15%）
- 摘要在章節「存入 Wiki」時同步生成並快取，避免每次生成時重複呼叫
- 摘要存儲於章節資料結構的 `summary` 欄位

**動態調整機制：**

- 系統根據所選模型的 context window 大小自動調整各區塊上限
- 若 Wiki 條目總量超出預算，優先保留與本章角色/地點相關的條目
- 用戶可在生成設置面板手動調整「參考深度」（淺層/標準/深度），對應不同的 token 預算策略

**運作流程：**

```
用戶點擊生成
    ↓
Context Budget Manager 計算可用 token 上限
    ↓
依優先級填入各內容區塊
    ↓
超出上限的區塊 → 壓縮摘要或截斷
    ↓
組裝最終 Prompt → 送出 LLM 請求
```

### 3.9 Multi-Agent 協作引擎（Phase 4，選做）

**核心概念：**
使用 Planner、Writer、Critic、Editor 四種專責 Agent 組成協作流水線，提升生成品質。此模組為選配，預設不啟用，用戶可在生成設置面板手動開啟。

**四種 Agent 角色：**

| Agent   | 職責 | 使用模型建議 |
|---------|------|-------------|
| Planner | 章節細綱優化、邏輯梳理、故事節拍細化 | 中大型模型 |
| Writer  | 撰寫初稿 | 大模型（高創意） |
| Critic  | 打分審核（風格、邏輯、一致性、人物、伏筆） | 大模型（嚴謹） |
| Editor  | 針對 Critic 意見進行潤色與優化 | 大模型或專用潤色模型 |

**迭代優化流程：**
1. Planner 產生優化後的章節細綱
2. Writer 撰寫初稿
3. Critic 給予詳細評分與改進建議（設定通過門檻，例如總分 ≥ 85）
4. 若未達標 → Editor 執行針對性重寫 → 回到 Writer 或 Critic
5. 最多迭代 3-4 次（可用戶調整）
6. 最終版進入版本歷史

**注意事項：**
- 完整跑一次迭代可能消耗大量 token（一章 10-20 萬 token），建議用戶先確認 API 費用或確保 Ollama 本機資源充足
- 開啟後建議先以單一章節測試，確認品質與成本後再批量使用

**使用模式：**
- **快速模式（預設）**：單 Agent，Writer 直接生成
- **高品質模式**：完整 Multi-Agent 迭代

**UI 位置：** 生成設置面板中新增「生成模式」切換。

## 五、技術選型

| 層級 | 技術方案 |

> **epub 技術說明：** epubjs 定位為電子書**閱讀器**，不適合用於生成 epub 檔案。epub 本質上是符合特定規範的 ZIP 壓縮包（包含 OPF、NCX/NAV、HTML 章節檔），建議改用 `epub-gen` 套件，或直接手寫 epub 結構以獲得最大控制彈性。

> **Ollama CORS 說明：** 本專案定位為本機運行，可直接呼叫 `localhost:11434`，無 CORS 問題。若未來考慮 Web 部署，需額外處理。

## 七、部署方式

- **本機 Web App（主要）**
  - 直接用瀏覽器開啟 `index.html`，或執行 `npx serve` 後於瀏覽器訪問
  - 所有資料存於本機 IndexedDB，不需要後端伺服器
